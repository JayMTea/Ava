# Plan: Device connectors hardening + the Ava device SDK

Status: **Phases 1–3 complete** (see the phase list below, which has said so for
some time while this header still read "Phase 1"). This is the plan of record for
making
"bring your own Arduino/ESP32/sensor and wire it to Ava" robust and doable
without a terminal, and for shipping a thin, **board-agnostic** SDK.

Shipped in Phase 1:

- **SDK** — `sdk/arduino/AvaClient` (dependency-free C++; push via any `Client`,
  pull via `handleHttp`/`handleStream`) and `sdk/host/ava_device` (Python push
  client + `serve_pull` facade + `SerialRelay`). Push+pull verified end-to-end.
- **Terminal-free on-ramp** — `GET /api/hub/connectors/{id}/ingest-token`
  (Push-token reveal+copy in the UI), a "This is a device" preset on the connect
  form, and a live `DeviceVerify` "waiting for first reading…" step
  (`GET …/last-event`).
- **Lifecycle** — `POST …/delete` (+ button; built-ins protected). There was no
  delete before.
- **Pull deploy automation** — `POST …/deploy` (one button = render + install
  into the sandbox), replacing the manual `cd agent && ./install.sh`; push-only
  devices report "nothing to deploy"; degrades gracefully when the sandbox is
  unreachable.

Deferred to Phase 2/3 below: enable/disable + edit, malformed-manifest
surfacing, fetch-error states, ingest rate-limit, endpoint reconciliation, and
the optional voice-announce hook.

## Objective

Let a user connect **their own** device through the connector workflow Ava
already has, and give them a small SDK so wiring a board takes a few lines —
both directions:

- **Push** — the device hands Ava events/readings when *it* decides
  (`POST /api/connectors/<id>/events`). Needs no sandbox deployment.
- **Pull** — Ava reads a sensor or sends a command on demand
  (`actions.discover`: `GET /tools`, `POST /call`). Needs the connector's
  egress policy deployed into the agent sandbox.

## Non-goals (guardrails — do NOT do these)

- No in-app hardware catalog or "pick your board." The board and its transport
  come entirely from the user's setup.
- No serial/BLE/MQTT/Zigbee/Matter transports baked into Ava's core. That stays
  in the device/host app, per `DEVICE_CONNECTORS.md`.
- No new ingestion pipeline, datastore, or rules engine. Reuse `devices.py` +
  `POST /api/connectors/<id>/events` as-is.
- A device is still just a `connector.yaml`. No parallel device abstraction.

## What already exists (reused, not rebuilt)

- Push ingest: `POST /api/connectors/<id>/events` → `ava_bridge/devices.py`
  (bounded JSONL) → live `device.event` SSE + active alerts + the agent's
  `device_events` tool. Per-connector bearer token `HMAC(root, "ava-ingest:<id>")`.
- Pull: `actions.discover` bridged live via `/internal/connector/<id>/__tools`
  and `__call`; egress auto-generated by `render_egress_policy`.
- CLI: `ava device new|token|events|list`.
- Manifest schema in `ava_bridge/connectors.py`; device template in `ava_cli.py`.
- Worked example: `examples/device-app/server.py` (both directions).

## The board-agnostic SDK (this repo: `sdk/`)

Nothing here is board-specific; everything is built on Arduino's standard
`Client` / `Stream` interfaces and stdlib Python.

### `sdk/arduino/AvaClient/` — Arduino/C++ library

- Push: user supplies their own `Client&` (WiFiClient, EthernetClient, …);
  `ava.reading(...)`, `ava.event(...)`.
- Pull: register capabilities with `addSensor(...)` / `addCommand(...)`; the
  library builds the `/tools` schema and dispatches `/call`. Answered over
  either transport:
  - `handleHttp(Client&)` — minimal HTTP for networked boards that serve
    their own `/tools` + `/call`.
  - `handleStream(Stream&)` — line-delimited JSON over any `Stream` (Serial,
    Serial1, a TCP stream), relayed by the host adapter. Serial-only boards
    also push via `emitReading()` / `emitEvent()` over the same stream.
- No external library dependencies (hand-rolled minimal JSON) so it compiles
  for whatever board the user has.

### `sdk/host/ava_device/` — host-side adapter (Python)

For boards without their own networking (classic Uno/Nano over USB) or users
who prefer a host bridge. Board-agnostic: the user picks the transport (serial
port, MQTT topic, …); the adapter provides:

- `AvaDevice(...).reading()/.event()` — the push client (token + retries).
- `serve_pull(...)` — the HTTP `/tools`+`/call`+`/health` facade Ava's
  `actions.discover` points at.
- `SerialRelay` — round-trips pull requests to an Arduino running
  `handleStream`, and forwards the board's push lines to Ava.

## Workstreams

- **A. Terminal-free on-ramp:** in-UI ingest-token issuance
  (`GET /api/hub/connectors/{id}/ingest-token`), a "device" preset on the
  existing connect form, and a live "waiting for first reading…" verify step.
- **B. SDK:** `sdk/arduino` + `sdk/host` + examples + a 5-minute doc. *(started)*
- **C. Lifecycle:** connector **delete** endpoint + button (none today),
  enable/disable toggle, edit.
- **D. Robustness:** surface malformed-manifest errors (today swallowed),
  ingest payload size cap + rate limit, render fetch-error states, reconcile
  the two connector-listing endpoints.
- **E. Pull deploy automation:** a "Deploy to agent" endpoint that runs
  `connector policies --write` + the runtime install for the active runtime
  (local NemoClaw directly; `remote` via the shim), falling back to showing the
  command only when the runtime is unreachable.

## Phasing

- **Phase 1 (push + pull, user-friendly):** A, B, C1 (delete), E. **✓ complete.**
- **Phase 2:** C2/C3 (enable/disable/edit), D1/D3. **✓ complete.**
  - Enable/disable via the manifest `enabled` flag (`POST …/enabled`); the Hub
    list now uses `connectors.catalog()` so disabled connectors stay visible and
    re-enablable, with a `builtin` flag gating edit/disable/delete.
  - Edit via a raw-manifest editor (`GET`/`POST …/manifest`), built-ins read-only.
  - Malformed manifests are captured (`connectors.load_errors()`) and surfaced in
    the Hub and in `ava doctor` instead of vanishing silently.
  - Fetch-error states rendered in the Hub connectors panel (with retry) and the
    Ops connectors panel, distinct from a genuine empty list.
- **Phase 3:** D2, D4, optional voice-announce hook. **✓ complete.**
  - Ingest rate limiting: per-connector token bucket (`devices.allow`, env-tunable
    `AVA_DEVICES_RATE_PER_MIN`/`_BURST`) → 429 on flood. (The 64 KB body cap and
    name/message length caps already existed.)
  - Reconciled the two listing endpoints by documenting them: `/api/hub/connectors`
    is the management view (incl. disabled + edit/deploy state), `/api/ops/connectors`
    is the dashboard telemetry view (enabled only + health/perf/egress) — kept
    separate on purpose, cross-referenced in both docstrings.
  - Voice-announce hook: opt-in "Speak alerts" toggle on the Ops Device-events
    panel speaks notify/warn/critical events via the Web Speech API — the
    `device.event` seam, no server voice subprocess. Persisted per browser.

All three phases complete. Remaining ideas (not scheduled): a server-side/on-device
voice path for announcements when no browser is open, and a device history view.
