What one manifest gives you

Every surface below is generated from your app's folder when Ava loads it. None of it is hand-maintained anywhere in Ava's core. Iframes and tool consoles need no rebuild; native React views require a private frontend build.

  • A tab in your sidebar

    Your app's UI behind Ava's authenticated proxy. The app keeps its own login unless SSO is configured. Set a separate apps origin to isolate it from Ava's browser interface.

  • A health row

    From one probe address. Name the feature switch that governs the service and a dead probe reads off rather than down, so a thing you turned off never looks like an outage.

  • Performance records

    If your app writes no performance log, the bridge writes one for it: every proxied call timed, with its status. A brand-new app shows recorded on its first call, with no restart.

  • Tools your AI may call

    Declared in the manifest, discovered live from your app's own tool list, or read straight off its MCP server. Ava generates tools for compatible runtimes; an external service owns its own registration.

  • An egress policy

    Ava renders the connector's declared destinations into policy for compatible sandbox runtimes. Enforcement depends on the runtime; an external agent service supplies its own execution boundary.

  • Application data

    Apps can return charts, query results, and source citations using documented artifact schemas. Saved artifacts preserve the app's identity and can be exported from chat.

{#- 5. The rest of the argument, and note what is NOT here: "chat with your documents", "runs locally", "speaks MCP". All true, all commodity, all demoted to a line inside a card rather than a card of their own. -#}

And then it watches all of it

An AI hub that cannot tell you how your own software is doing is just a chat window with extra steps.

  • Your apps' ops console, not just your AI's

    Check service health and hardware in Setup. Request performance records through agent tools when configured. Cost and energy depend on available measurements and operator-supplied rates.

  • The agent is what is contained, not your server

    MCP servers run host-side and connector calls pass through the bridge's authorization and consent checks. Stdio servers and Python extensions are trusted code; sandboxing depends on your chosen runtime.

  • Your model, your rules

    No default language model ships. Choose an inference backend, write your persona, and select NemoClaw or another runtime. Voice processing is optional and needs separately installed dependencies.

  • It says NOT MEASURED

    Ava names the model class your machine can hold before you download one, and where a claim about your hardware is unverified it says so instead of rounding up. The installer prints that verdict before it installs anything.

One command

The installer detects your hardware, picks a profile, resolves your model's flags, and waits for the app to actually answer before it says it is done.

{#- Two lines, not the 67-character && one-liner in deploy/README.md. A command that visually wraps is a command somebody mistypes, and 67 characters cannot fit the 296px a 320px viewport leaves. Same operation, and deploy/README.md already uses a two-line shape for Windows. -#}
git clone {{ config.repo_url or 'YOUR_REPOSITORY_URL' }} Avacd Ava/deploy && ./install.sh

It finishes by printing a one-time link. Open that whole link to set your password. Continue in Setup to choose a model, connect your apps, configure optional voice, and set budgets. Ava is a web app, so it installs to your phone from the browser too.

What needs a setup step first. Web search is off by default, and the shipped Docker profiles do not provision SearXNG or Tor yet, so it is opt-in setup rather than on out of the box. Voice is off by default, and under Docker it needs an image built with AVA_VOICE_DEPS=1. The NemoClaw adapter needs its CLI installed first. You can instead connect an external runtime service. Capabilities and sandbox enforcement depend on the runtime you choose.
